# 仓库分析计划

## Summary

- 目标：对 `/workspace` 下的 `WritingCoach` 仓库做一份“架构拆解 + 演进建议”的中等深度分析，帮助快速理解模块边界、主调用链、数据流与后续扩展方向。
- 输出形式：执行阶段不修改业务源码，直接基于现有代码向用户交付一份结构化分析说明。
- 分析范围：根 `SwiftPM` 包、`WritingCoachCore`、`WritingCoachCLI`、`Apps/WritingCoachMacApp`、`Apps/WritingCoachiOSApp`、现有测试目录。
- 不在本次范围：实现新功能、重构代码、补测试、运行写操作命令或变更仓库配置。

## Current State Analysis

### 仓库结构

- 根工程是 `Swift Package Manager` 项目，定义于 `/workspace/Package.swift`。
- 根包产物包括库 `WritingCoachCore` 和可执行程序 `writingcoach`，源码分别位于 `/workspace/Sources/WritingCoachCore` 与 `/workspace/Sources/WritingCoachCLI/main.swift`。
- 图形界面分为两个独立子工程：
  - `/workspace/Apps/WritingCoachMacApp`
  - `/workspace/Apps/WritingCoachiOSApp`
- 测试集中在 `/workspace/Tests/WritingCoachCoreTests`，当前覆盖 Front Matter、导入器、规则引擎、ULID 等核心能力。

### 已确认的架构事实

- 核心服务入口是 `/workspace/Sources/WritingCoachCore/WritingCoachService.swift`，统一封装创建、保存、加载、分析、列表查询。
- 文档正文采用 Markdown 文件落盘，路径规则由 `/workspace/Sources/WritingCoachCore/LibraryLayout.swift` 与 `/workspace/Sources/WritingCoachCore/DocumentFileStore.swift` 定义。
- 索引与标签采用 SQLite，主要实现位于 `/workspace/Sources/WritingCoachCore/DocumentIndexStore.swift`。
- 文本分析链路为：`DocumentFileStore` 读取正文 -> `Analyzer` 构建 `AnalysisContext` -> `RuleEngine` 产出 `Suggestion`。
- 导入链路为：`WeChatHTMLImporter` 将 HTML 转为 Markdown，并通过 `AssetStore` 落资源、通过 `DocumentIndexStore` 写索引。
- macOS 与 iOS App 都直接依赖 `WritingCoachCore`，说明仓库采用“核心能力复用 + 多前端壳”的组织方式。

### 已观察到的演进信号

- `/workspace/Sources/WritingCoachCore/DocumentIndexStore.swift` 已建表 `voice_profiles`、`imports`、`suggestion_feedback`，但当前核心代码里未看到与这些表匹配的完整读写闭环，说明存在预留能力。
- 当前测试主要覆盖核心单点能力，尚未看到跨层集成分析，例如“创建文档 -> 写入索引 -> 分析 -> 前端/CLI 消费”的完整回归链路。
- CLI 已提供 `init/new/list/import-wechat-html/analyze`，但 App 入口与 CLI 入口之间的能力暴露方式仍较轻量，适合在分析中讨论后续统一应用服务边界。

## Proposed Changes

### 交付内容

- 产出一份面向接手开发者的仓库分析，覆盖：
  - 顶层结构与技术栈
  - 核心模块职责拆分
  - 关键调用链与数据流
  - CLI / macOS / iOS 三类入口关系
  - 当前设计优点、局限与可演进方向
  - 测试覆盖现状与后续建议

### 执行步骤

1. 基于现有勘察结果整理仓库全景，先说明根包、Core、CLI、Apps、Tests 的关系。
2. 提炼 `WritingCoachCore` 的领域模型与分层职责，明确“文件真源 + SQLite 索引 + 规则引擎”的核心设计。
3. 串起三条关键流程：
   - 新建/保存文档
   - 文档分析出建议
   - 微信 HTML 导入入库
4. 从 App 与 CLI 入口反推公共能力暴露边界，说明当前复用方式和潜在耦合点。
5. 基于预留表、测试覆盖和当前模块边界，给出演进建议，区分“短期可做”和“中期可演进”。
6. 最终用结构化中文回答直接交付给用户，保持中等深度，避免过度下钻到实现细枝末节。

### 演进建议的组织方式

- 短期建议：聚焦补齐闭环和提升可维护性，例如补集成测试、收敛服务边界、把预留表能力与业务接口对齐。
- 中期建议：聚焦架构演进，例如抽象应用层用例、引入更清晰的同步/异步边界、完善风格画像与建议反馈闭环。
- 明确说明这些建议来自现有代码状态，不假设未在仓库中出现的外部系统或运行环境。

## Assumptions & Decisions

- 用户当前需要的是分析方案，而不是立刻执行完整分析输出。
- 这次重点锁定为“架构拆解 + 演进建议”，深度为“中等深度”。
- 执行阶段默认不做源码修改，除非用户在批准计划后追加实现需求。
- 分析结论仅基于当前仓库实际文件与代码，不推测未出现的部署系统、后端服务或外部依赖。

## Verification Steps

- 核对最终分析是否覆盖以下六项：
  - 仓库结构
  - 模块职责
  - 数据流
  - 入口关系
  - 风险/演进点
  - 测试现状
- 确认所有路径与结论都能回溯到已读取的真实文件。
- 确认输出语言为中文，粒度符合“中等深度”，既能帮助理解，也不会泛泛而谈。
